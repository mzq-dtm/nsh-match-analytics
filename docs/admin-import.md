# 管理员导入指南

本文是联赛数据网页导入的操作与数据格式说明，适用于经典服联赛导入模式和黄金畅玩服联赛导入模式。两种模式最终使用同一套后端预检、备份和事务写入流程；区别只在于黄金畅玩服联赛数据会先在浏览器中推断真实团队团长并改写本帮记录的“所在团长”。

导入会写入正式数据库。管理员应先完整检查源文件、比赛时间、胜负和玩家身份，再执行最终提交。

## 权限与运行前提

- 只有受信任的管理员可以访问 `/admin/import` 和 `/admin-api/*`。
- 应用本身没有管理员登录功能。生产环境必须由 Nginx、反向代理或其他接入层保护管理员页面和管理员 API；部署方式见[生产部署指南](deployment.md#架构与安全边界)。
- 管理员后端端口 `10291` 只能绑定本机地址，不能直接暴露到公网或不可信内网。通过公网或其他不可信网络访问时必须使用 HTTPS，避免 Basic Auth 凭据和 CSV 内容以明文传输。
- 按仓库提供的 Nginx 配置部署时，管理员账号还需要能够读取受普通用户认证保护的静态资源，否则页面可能打开但资源加载失败。
- 管理员服务的运行用户必须能够读写 SQLite 数据库、`ADMIN_UPLOAD_DIR` 和 `DB_BACKUP_DIR`；上传目录和备份目录还应有足够磁盘空间。
- 管理员后端应保持单 worker。它与查询后端必须指向同一份 SQLite 数据库。
- 本帮帮会必须已经存在于数据库，页面填写的本帮帮会名必须与数据库和联赛 CSV 完全一致。同一帮会更名后，应先按[生产部署指南](deployment.md#已有生产库登记更名后的本帮名称)登记新名称。

本地开发环境没有应用层认证。启动前端、查询后端和管理员后端后，可访问 `http://127.0.0.1:5173/admin/import`。

## 导入前检查清单

开始前确认以下事项：

1. 联赛数据 CSV 和帮会成员 CSV 来自同一场比赛附近的有效导出，未混入其他场次的数据。
2. 联赛数据文件名包含正确的比赛时间，且该时间严格晚于数据库中的最新比赛。
3. 联赛 CSV 只包含本帮和一个对方帮会，并且双方数据均存在。
4. 本帮胜负选择正确；备注内容无需写入时保持为空。
5. 两份 CSV 的必需表头、编码、整数格式和昵称唯一性符合本文要求。
6. 黄金畅玩服联赛导入时，帮会成员 CSV 中的分堂、职位和总战力足以支持团长与小队推断。
7. 生产环境的数据库备份目录可写且空间充足。

系统不支持倒序补录、覆盖或在网页中撤销导入。发现历史场次遗漏时，不要先导入更新场次；应先按时间顺序处理遗漏数据。

## 完整操作流程

1. 从“联赛数据”页面点击“导入数据”，或直接打开 `/admin/import`。
2. 填写本帮帮会名，选择本帮“胜利”或“败北”，按需填写备注。
3. 选择联赛数据 CSV 和帮会成员 CSV，点击“识别格式并继续”。
4. 页面只统计本帮记录，并根据原“所在团长”分组识别导入模式。先检查页面显示的模式、人数和判定依据。
5. 如果识别为经典服联赛数据，浏览器会直接把原联赛 CSV 送入后端预检。
6. 如果识别为黄金畅玩服联赛数据，先确认真实团队团长，再检查自动推断和待人工选择的小队；页面生成改写结果后才进入后端预检。
7. 在后端预检结果中核对比赛名称、比赛时间、本帮、对方和双方记录数。
8. 对页面列出的每个昵称，核实并输入玩家 ID。没有待确认项时可直接继续。
9. 再次确认胜负和备注，点击“确认并导入”。提交会获取数据库写锁、创建导入前备份，并在一个事务中写入全部数据。
10. 看到成功消息后，按[导入后核验](#导入后核验)检查展示结果和备份。

预检后，若要更换任一 CSV 或本帮帮会名，应先点击“清空”并重新开始。浏览器为黄金畅玩服联赛数据生成的改写文件只用于本次上传，不会修改用户电脑上的原文件。

## CSV 通用契约

### 文件与表头

- 两个文件的扩展名都必须是 `.csv`，扩展名大小写不敏感。
- 使用 UTF-8 或 UTF-8 BOM 编码。系统不会自动识别 GBK、ANSI 等其他编码。
- CSV 使用英文逗号分隔，并遵循标准引号转义规则。字段中含英文逗号、双引号或换行时，应由导出程序正确加引号。
- 两份文件连同 multipart 请求开销的总大小不能超过 16 MiB。
- 表头名称必须与本文完全一致。列顺序可以不同，也可以包含系统不使用的额外列。
- 不要给表头添加首尾空格。浏览器识别会修剪表头，但后端按 CSV 中的实际列名校验。
- 空白行会被忽略。联赛 CSV 中重复出现的内嵌表头行会按“帮会名”列过滤，但不应依赖此行为整理数据。

### 文本字段

联赛 CSV 的“帮会名”“玩家”“职业”“所在团长”都会去除首尾空格，然后再参与匹配和写入：

- 本帮帮会名和每行帮会名最长 100 个字符。
- 玩家昵称和团长昵称最长 64 个字符。
- 职业名最长 50 个字符，且必须与数据库职业表中的名称完全一致。
- 上述字段不能为空，不能包含尖括号、控制字符或不可见格式字符。
- 大小写、简繁体和内部空格不会自动归一化。

帮会成员 CSV 中的非空“名称”同样会去除首尾空格，最长 64 个字符，并禁止尖括号、控制字符和不可见格式字符。成员表的分堂、职位等辅助字段不采用上述全部文本校验，但仍应保持游戏导出的原始、可读值。

### 整数字段

联赛 CSV 的所有数值字段必须填写。帮会成员 CSV 的“装评”“修为”“修炼”“总战力”可以留空，空值按 `0` 处理。

非空整数必须同时满足：

- 只包含 ASCII 字符 `0` 至 `9`；
- 为非负整数；
- 去除首尾空格后，不包含正负号、小数点、千位分隔符、单位、内部空格或全角数字；
- 数值不超过 SQLite 有符号 64 位整数上限 `9223372036854775807`。

首尾空格会被修剪，前导零可以读取，但建议不要保留。

### 唯一性与帮会范围

- 经典服联赛导入模式和黄金畅玩服联赛导入模式都禁止重复数据。
- 联赛 CSV 内，同一帮会中同一玩家昵称只能出现一次；即 `(帮会名, 玩家)` 必须唯一。同一昵称出现在本帮和对方各一行不视为重复。
- 帮会成员 CSV 中每个非空“名称”只能出现一次。该要求对两种导入模式都适用。
- 联赛 CSV 必须同时包含本帮和且仅一个对方帮会。去重后应正好是两个帮会名。
- 帮会成员 CSV 可以包含未参赛成员。成员表中缺少某位本帮参赛玩家时，该玩家的装评、修为、修炼和总战力按 `0` 写入。
- 帮会成员 CSV 只用于补充本帮数据；对方战绩不关联成员表。

## 联赛数据 CSV

必需列共 16 列：

```text
帮会名、玩家、等级、职业、所在团长、击败、助攻、战备资源、
对玩家伤害、对建筑伤害、治疗值、承受伤害、重伤、青灯焚骨、化羽、控制
```

其中“等级”及从“击败”到“控制”的统计列均属于必填整数字段。

最小结构示例：

```csv
帮会名,玩家,等级,职业,所在团长,击败,助攻,战备资源,对玩家伤害,对建筑伤害,治疗值,承受伤害,重伤,青灯焚骨,化羽,控制
本帮名称,玩家甲,80,血河,本帮团长,5,10,100,200000,30000,0,150000,2,0,0,3
对方名称,玩家乙,80,铁衣,对方团长,2,8,90,120000,20000,0,210000,4,0,0,5
```

### 文件名与比赛时间

联赛 CSV 文件名必须包含一个有效的 `YYYY_MM_DD_HH_MM_SS` 时间戳。例如：

```text
联赛数据_2026_08_18_20_30_00.csv
```

后端从文件名中找到第一个符合该格式的片段，并据此生成比赛时间和标准比赛名称：

```text
本帮名称vs对方名称_2026_08_18_20_30_00.csv
```

该时间不携带时区信息，应统一使用部署所约定的本地比赛时间。它必须严格晚于数据库中所有已有比赛的最新时间；相同或更早的时间都会被拒绝。因此：

- 不能倒序补录历史比赛；
- 不能用相同时间覆盖已导入比赛；
- 修改原文件名的其他部分不会绕过重复比赛或时间顺序检查。

## 帮会成员 CSV

### 经典服联赛导入模式

必需列共 5 列：

```text
名称、装评、修为、修炼、总战力
```

“名称”为空的行会被忽略。“名称”按去除首尾空格后的结果与本帮参赛昵称精确匹配。四个数值字段允许为空，空值或未匹配到成员行时按 `0` 写入。

最小结构示例：

```csv
名称,装评,修为,修炼,总战力
玩家甲,100000,20000,30000,150000
```

经典服联赛导入模式会保留联赛 CSV 中本帮和对方的原“所在团长”，不执行团长或小队推断。

### 黄金畅玩服联赛导入模式

帮会成员 CSV 必须同时满足后端成员属性要求和浏览器推断要求，因此至少包含 7 列：

```text
名称、分堂、职位、装评、修为、修炼、总战力
```

示例：

```csv
名称,分堂,职位,装评,修为,修炼,总战力
玩家甲,青龙堂,青龙堂主；管理,100000,20000,30000,150000
```

额外规则如下：

- 至少要有一个去除首尾空格后以“堂”结尾的分堂名称；其他分堂值会视为无有效分堂。
- 多个职位使用中文分号 `；` 或英文分号 `;` 分隔。堂主识别要求其中一个拆分后的职位精确等于“`分堂名`主”，例如“青龙堂主”。
- 用于自动推荐时，“总战力”必须为 ASCII 非负整数；空值或格式错误会被视为无法比较。非空格式错误的数据仍会在后端预检中被拒绝，不能靠手工选择团长绕过。
- 参赛玩家不在成员表中时仍可能成为团长候选，但其分堂和总战力未知，需要管理员人工判断。

## 导入模式识别规则

识别是根据 CSV 结构进行的启发式判断，不是服务器身份校验。系统只统计“帮会名”与页面所填本帮帮会名一致的行，并忽略原“所在团长”为“无”的记录后计算：

1. 如果任一原“所在团长”名下至少有 7 人，识别为经典服联赛数据。
2. 否则，如果不同原“所在团长”不超过 6 个，识别为经典服联赛数据。
3. 否则，也就是所有分组都少于 7 人且不同原“所在团长”超过 6 个，识别为黄金畅玩服联赛数据。

原“所在团长”为“无”的玩家不参与上述团长数和单组人数统计，但仍属于本帮参赛记录，会正常预检和导入。
如果本帮所有记录的原“所在团长”都是“无”，排除后的团长数为 0，当前启发式会按“不超过 6 个”识别为经典服联赛数据；管理员必须结合实际来源判断该结果是否合理。

页面会显示本帮记录数、排除“无”后的团长数、单个团长最大人数和每组统计。此规则可能被异常或不完整的源数据误导，而且当前页面没有手工切换模式的选项。识别结果与实际不符时不要继续导入，应先修正源数据中的帮会名或“所在团长”内容，再重新识别。

## 经典服联赛导入模式

经典服联赛数据不需要浏览器改写：

1. 页面完成模式识别后，直接把原联赛 CSV 和成员 CSV 上传到后端。
2. 后端验证双方帮会、职业、整数、重复昵称、比赛时间和当前数据库状态。
3. 页面展示预检摘要和需要确认的玩家 ID。
4. 管理员确认后执行最终提交。

联赛 CSV 中的“所在团长”会直接成为本帮玩家的团长身份依据，因此导入前应检查其确实是团队团长，而不是临时小队长。

## 黄金畅玩服联赛导入模式

黄金畅玩服联赛 CSV 的原“所在团长”用于表示小队分组。浏览器结合成员表的分堂、职位和总战力，将这些小队归到管理员确认的真实团队团长名下。

### 团长候选与默认推荐

只有同时满足以下条件的玩家才能作为可选团长：

- 是本场本帮参赛玩家；
- 原“所在团长”不等于“无”。

系统针对成员表中每个有效分堂按以下顺序生成默认团长配置：

1. 查找职位列表精确包含“`分堂名`主”的成员。
2. 如果其中恰有一人也是本场可选团长，推荐该玩家；即使其成员表分堂与职位代表的分堂不同，也会按职位推荐并显示警告，必须人工复核。
3. 如果找到多名符合条件的参赛堂主，不自动选择，由管理员处理。
4. 如果成员表存在该堂堂主、但没有任何堂主是本场可选团长，才尝试从该堂的参赛候选中推荐总战力唯一最高者。
5. 如果成员表完全没有该堂堂主、没有符合条件的参赛成员、任一待比较成员的总战力无效，或最高总战力并列，都不自动推荐。

推荐只是初始值。管理员可以更换、新增或删除配置，但最终必须满足：

- 至少配置一名团长；
- 团长必须来自可选团长列表；
- 同一玩家不能被重复选为多个团队团长；
- 一个分堂只能对应一名团长；
- 分堂必须来自成员 CSV 中识别出的有效分堂；
- 不要求每个有效分堂都配置团长。

### 小队归属推断

系统按原“所在团长”的精确值把本帮参赛玩家分成原小队；原值为“无”的玩家不组成小队，并始终保持“无”。其他原小队依次按以下规则处理：

1. 原小队内恰好包含一名已配置团长时，整个小队自动归属该团长。
2. 原小队内包含多名已配置团长时，归属不明确，管理员必须先修改团长配置。
3. 原小队不包含已配置团长、人数至少为 4 且至少 4 名成员属于同一分堂时，系统认为该堂达成分堂共识；如果该堂已配置团长，则自动归属该团长。
4. 达成分堂共识但该堂没有配置团长时，该小队进入待人工选择。
5. 原小队少于 4 人，或没有任何分堂达到 4 人时，也进入待人工选择。
6. 待定小队可以从所有已配置团长中选择，不要求与推断分堂相同，最终决定由管理员负责。
7. 每名真实团长最多接收 5 个原小队。这里限制的是小队数，不是玩家数。

确认后，浏览器会生成一份内存中的联赛 CSV：只把本帮行的“所在团长”改为推断或人工选择的真实团长，对方帮会行和其他列保持原样。生成结果会沿用原文件名，以便后端提取比赛时间。

## 后端预检

后端预检不会写入业务表。它会：

- 保存两份上传文件到权限受限的随机暂存目录；
- 重新读取和验证 CSV 必需列、字段、整数及重复昵称；
- 确认本帮存在、只存在一个对方帮会、双方均有战绩；
- 确认双方所有职业都存在于数据库职业表；
- 从文件名解析比赛时间，检查比赛未导入且时间严格递增；
- 按比赛时间点匹配本帮玩家及其真实团长的昵称历史；
- 记录当前比赛表版本，并返回比赛摘要、待确认玩家和一枚随机预检令牌。

预检令牌和暂存文件有效期为 1 小时。过期后必须重新上传。预检后的文件由服务器保存，提交不会信任浏览器再次发送的 CSV。

对方帮会不必预先存在：最终提交时如果找不到同名帮会，系统会自动创建。对方玩家只按本场昵称保存为快照，不建立玩家 ID 或昵称历史。

## 玩家 ID 与昵称历史

后端以比赛时间为基准，查找昵称在该时刻有效的本帮玩家身份。检查范围包括：

- 本帮所有参赛玩家；
- 本帮数据中“所在团长”引用的所有昵称；
- 不包括对方玩家。

以下情况会要求管理员输入玩家 ID：

- `not_found`：比赛时间点找不到有效的昵称记录；
- `inactive`：找到了身份，但距该玩家上次参赛超过 29 天。

长期未参赛时，页面会在“原玩家 ID”列显示已有 ID，但“确认后的玩家 ID”输入框仍需管理员手动填写。确认仍是同一玩家时填入原 ID；确认已经换人时填入新玩家的游戏 ID。不要根据昵称相似度猜测，也不要把多个不同玩家填成同一个 ID。

玩家 ID 必须以字符串形式提交，并且只包含 ASCII 数字。后端当前校验范围是 `2` 至 `9223372036854775807`，但查询 API 和浏览器仍有环节使用 JavaScript `number`：超过 `9007199254740991` 后可能发生精度丢失。因此，在 API 全链路改为字符串之前，当前实际应只使用 `2` 至 `9007199254740991` 的玩家 ID，即使更大的值可能通过后端最终提交校验。

提交新身份时，系统会按本场比赛时间结束受影响的旧昵称记录，并为确认后的玩家 ID 建立新的昵称历史。若玩家 ID 与既有记录发生唯一性或关联冲突，整次导入会失败并回滚。

## 最终提交、备份与并发

点击“确认并导入”后，管理员后端依次执行：

1. 用暂存文件重新完成准备和校验，确认文件状态与预检一致。
2. 通过 `BEGIN IMMEDIATE` 获取 SQLite 写锁，最长等待约 15 秒。
3. 比较预检时记录的比赛数量、最新比赛 ID 和最新比赛时间。如果其他导入已改变比赛数据，本次提交会被拒绝。
4. 再次验证重复比赛、时间顺序、本帮、职业和待确认玩家，并校验提交的所有玩家 ID。
5. 在 `DB_BACKUP_DIR` 使用 SQLite Online Backup API 创建导入前数据库快照。
6. 在同一事务中写入比赛、胜负、备注、本帮战绩、对方战绩、必要的对方帮会和昵称历史。
7. 全部成功后提交事务并删除本次暂存目录；任一步失败则回滚业务写入。

备份创建失败会阻止导入。备份成功后如果后续写入失败，备份文件仍可能保留，这是正常的安全行为。系统不会自动清理旧备份，恢复方法和保留策略见[生产部署指南的“备份与恢复”](deployment.md#备份与恢复)。

SQLite 同一时间只能有一个写入者。多个管理员可以分别完成预检，但第一个成功提交会改变数据库版本；其他旧预检随后会收到“预检后数据库已经发生变化”，必须重新上传并预检。数据库长时间被其他写入占用时会返回冲突错误，应确认没有异常写任务后再重试。

## 错误处理

页面显示错误时，不要连续重复点击提交。先根据错误类别处理：

| 现象或消息 | 常见原因 | 处理方式 |
| --- | --- | --- |
| 无法识别导入文件、缺少列 | 编码、表头或 CSV 引号格式不正确 | 转为 UTF-8，核对精确表头并重新导出 |
| 玩家在同一帮会中重复、成员昵称重复 | CSV 存在重复行或重名行 | 找到提示中的首次行和重复行，只保留正确记录；两种导入模式都不能跳过此检查 |
| 无法唯一识别对方帮会 | 文件包含零个或多个非本帮帮会，或本帮名称填写错误 | 核对本帮名称并只保留本场双方数据 |
| 数据库中不存在职业 | CSV 职业名与数据库种子数据不一致，或旧库缺少新职业 | 不要改成近似名称；先由运维人员确认数据库职业数据 |
| 昵称对应玩家 ID 但没有历史战绩 | 玩家或昵称历史被手工写入，数据状态不符合导入假设 | 停止导入并由运维人员核对 `players`、`nickname_history` 与战绩关联；该情况不会转为玩家 ID 确认项 |
| 只能按时间顺序导入更新的比赛 | 文件名时间不晚于数据库最新比赛 | 停止导入，按时间顺序处理；不能通过改业务数据伪造时间来覆盖 |
| 比赛已经导入 | 相同标准比赛名称已存在 | 到联赛页面核对已有记录，不要重复提交 |
| 预检记录不存在或已经过期 | 超过 1 小时、暂存目录被清理或令牌无效 | 清空页面，重新上传并预检 |
| 预检后数据库已经发生变化 | 其他管理员已完成导入 | 重新上传，基于最新数据库再次预检 |
| 数据库正在执行其他写入 | SQLite 写锁在等待时间内未释放 | 等待当前写入完成；持续出现时检查管理员服务日志 |
| 数据违反唯一性或关联约束 | 玩家 ID 冲突、重复比赛数据或数据库状态异常 | 不要换一个随机 ID；核对身份并查看管理员服务日志 |
| 数据库备份失败 | 备份目录权限、磁盘空间、inode 或数据库读取有问题 | 本次导入未执行；修复备份条件后重新提交或重新预检 |
| 上传文件过大 | 单次请求超过 16 MiB | 确认文件没有混入其他场次；不要通过删除必需列规避校验 |
| 服务器内部错误 | 未预期异常 | 停止操作，查看 `nsh-admin` 日志后再决定是否重试 |

如果提交失败，业务事务会回滚，但暂存预检或已经生成的导入前备份可能仍然存在。不要仅凭“出现了备份文件”判断导入成功，应以 API 成功消息和业务页面核验为准。

## 导入后核验

每次成功导入后至少完成以下检查：

1. 记录成功消息中的标准比赛名称、本帮条数和对方条数。
2. 打开“联赛数据”，确认新比赛时间、对手、胜负和备注正确。
3. 核对页面中的本帮和对方人数与预检结果一致，并抽查双方关键统计。
4. 经典服联赛数据抽查原“所在团长”是否正确；黄金畅玩服联赛数据抽查真实团队团长映射，特别是人工选择的小队和原值为“无”的玩家。
5. 对本次新建、改名或长期未参赛的玩家，打开玩家历史确认昵称和历史归属正确。
6. 在服务器确认 `DB_BACKUP_DIR` 出现本次导入前的数据库备份，并按运维策略复制到异机或对象存储。
7. 如需进一步确认数据库完整性，按[生产部署指南](deployment.md#9-部署验证)执行健康检查和 SQLite 检查。

如果发现错误，不要尝试通过再次导入相同比赛来覆盖，也不要继续导入时间更晚的比赛。立即停止后续导入，保留成功消息、源 CSV、管理员服务日志和对应的导入前备份，再由运维人员按恢复流程处理。
